---
title: Gate drift in CI
description: Fail a build when the .gitignore no longer matches its header, through a check script or the composite action this repository ships.
icon: lucide:shield-check
---

`gitignore-sync check` is a dry run. It reconciles the file, reports what it
found and whether the file is in sync, and exits non-zero when the result
differs from what is on disk — a stale section, a hand edit inside a block, a
stack added to the header and never rendered. It writes nothing, and it does
not print the resulting file: `gitignore-sync sync --dry-run` does that.

## Through the check script

A repository whose CI derives its task list from `package.json` — as
`kirchDev/workflows`' shared check workflow does — needs no workflow change at
all. Add the command to the `check` script and it comes along:

```json
{
  "scripts": {
    "check": "… && gitignore-sync check"
  }
}
```

This needs `@kirchdev/gitignore-sync` as a dev dependency, which also pins the
version through the lockfile.

## Through the action

For a repository without such a script, `action.yml` at the root of this
repository is a composite action wrapping the same command. It adds a job summary
on failure and a `status` output (`in-sync` or `drifted`); its inputs are
documented in the file itself.

```yaml
- uses: actions/checkout@v7
- uses: kirchDev/gitignore-sync@vX.Y.Z
  with:
    version: 'X.Y.Z'
```

Pin `version`. Its default is `latest`, which lets a new release — a template
gaining a version, say — turn a green pipeline red on its own.

## Monorepos

`check --recursive` checks every managed region below the directory and skips
files that carry none, so it never fails on an unmanaged sub-directory. The
action runs a plain `check` on one directory; use the script form for a
recursive gate. See [Nested .gitignore files](/concepts/nested-gitignores).

## Result

A drifted `.gitignore` now fails the build instead of rotting. The fix is always
the same: run `gitignore-sync sync` and commit the result.

::callout{type="info" title="Why a composite action"}
The exit code is the whole result, so the action wraps the published CLI rather
than bundling a second copy of it. An action that writes comments or check runs
of its own would earn a bundle; this one does not.
::
